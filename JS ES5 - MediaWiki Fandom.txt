JavaScript ES5 — дополнение: работа с MediaWiki и Fandom
=========================================================

Этот файл дополняет общую справку по ES5 и объясняет, как на практике работать с MediaWiki и
wiki-сайтами на базе MediaWiki, включая многие вики на Fandom.

Главная идея:
- MediaWiki — это движок вики;
- многие вики на Fandom тоже работают на MediaWiki-подобной базе;
- почти вся автоматизация идёт через API;
- в ES5 чаще всего используют XMLHttpRequest, JSON.parse, JSON.stringify, setTimeout,
  а для сложных задач — токены, сессии и аккуратную обработку ответов.

------------------------------------------------------------
1. Что такое MediaWiki в практическом смысле
------------------------------------------------------------

MediaWiki — это движок, на котором работают вики-сайты.
Он хранит:
- страницы;
- историю правок;
- категории;
- шаблоны;
- файлы;
- пользователей;
- обсуждения;
- служебные данные.

Для разработчика важны три уровня:

1) Вики-разметка
   Это текст страниц, написанный в стиле wiki markup.

2) HTML-вывод
   То, что видит браузер после обработки разметки.

3) API
   Машинный интерфейс для чтения и изменения данных.

Если писать скрипт на JavaScript ES5, обычно используют API,
потому что:
- проще получать структурированные данные;
- можно автоматизировать поиск, анализ и правки;
- не нужно парсить HTML вручную без необходимости.

------------------------------------------------------------
2. Главные API-интерфейсы
------------------------------------------------------------

У MediaWiki есть несколько API, но в повседневной работе важнее всего два:

- Action API — классический интерфейс через api.php;
- REST API — более современный интерфейс через rest.php.

Для большинства старых и средних автоматизаций чаще встречается Action API.
Именно с ним проще всего связывать ES5-код.

Практический вывод:
- если нужен список страниц, категории, история, содержимое, токены и правки — смотри Action API;
- если нужен более современный REST-подход, смотри REST API;
- для старого JS-кода и скриптов чаще всего начинают с api.php.

------------------------------------------------------------
3. Базовый принцип работы с API
------------------------------------------------------------

Обычно последовательность такая:

1) Отправить запрос.
2) Получить JSON.
3) Проверить ошибки.
4) Преобразовать или сохранить данные.
5) При необходимости отправить следующий запрос.

Типичный адрес выглядит так:

    https://example.fandom.com/api.php?action=query&format=json

Но параметры меняются в зависимости от задачи.

Самое важное:
- `action` задаёт действие;
- `format=json` говорит вернуть JSON;
- дополнительные параметры уточняют, что именно получить.

------------------------------------------------------------
4. Чтение содержимого страницы
------------------------------------------------------------

Один из самых частых сценариев — получить текст страницы.

Обычно это делают через `action=query` и `prop=revisions`.
По документации MediaWiki, revisions API можно использовать, чтобы получить данные по одной
или нескольким страницам, включая содержимое последней ревизии.

Что это даёт:
- читать wikitext;
- анализировать страницы;
- искать шаблоны;
- переносить данные в другой формат.

Пример запроса:

    api.php?action=query&prop=revisions&titles=Main_Page&rvprop=content&format=json

Что делает этот запрос:
- `query` — режим чтения данных;
- `prop=revisions` — взять данные о правках;
- `titles=Main_Page` — выбрать страницу;
- `rvprop=content` — попросить текст содержимого;
- `format=json` — вернуть JSON.

Типичный сценарий на ES5:
- открыть `XMLHttpRequest`;
- получить JSON;
- извлечь текст из ответа;
- разобрать его регулярными выражениями или строковыми методами.

Важно помнить:
- страница может не существовать;
- может быть несколько страниц в ответе;
- названия страниц могут приходить в неудобной форме;
- у разных вики структура ответа одна и та же, но данные внутри отличаются.

------------------------------------------------------------
5. Парсинг wikitext
------------------------------------------------------------

Иногда нужен не исходный текст, а HTML, уже обработанный движком.

Для этого используют `action=parse`.

Что это даёт:
- получить HTML из wikitext;
- посмотреть, как страница рендерится;
- разобрать шаблоны уже после подстановки;
- получить фрагменты страницы.

Пример:

    api.php?action=parse&page=Main_Page&format=json

Можно использовать и для анализа отдельных участков страницы,
если нужна не вся страница целиком, а именно результат парсинга.

Где это полезно:
- предпросмотр;
- извлечение блоков;
- автоматическая проверка шаблонов;
- сбор контента для скрипта или бота.

Осторожно:
- HTML из parse может содержать много лишней служебной разметки;
- HTML нужно обрабатывать аккуратно;
- для простой логики иногда лучше читать wikitext, а не HTML.

------------------------------------------------------------
6. Поиск страниц
------------------------------------------------------------

Для поиска страниц используется `action=query` с поисковыми параметрами.
В официальной документации есть модуль поиска для страниц по заголовку или тексту.

Что это позволяет:
- найти страницы по ключевому слову;
- построить свой поиск;
- проверить, существует ли статья;
- собрать список релевантных страниц.

Практическая логика:
- отправить поисковый запрос;
- посмотреть заголовки;
- при необходимости открыть каждую страницу отдельно.

Это полезно, если:
- нужно массово обрабатывать страницы;
- требуется найти статьи по категории;
- надо сравнить названия;
- нужен автосбор ссылок.

------------------------------------------------------------
7. Категории
------------------------------------------------------------

Категории — один из основных способов структурировать страницы вики.

В MediaWiki есть API для:
- получения категорий страницы;
- получения страниц внутри категории;
- получения списка категорий.

Что это значит practically:
- можно узнать, к каким категориям относится статья;
- можно собрать все страницы по теме;
- можно автоматизировать навигацию.

Пример логики:
- запросить категорию;
- получить список страниц;
- пройтись по ним в цикле;
- собрать данные в массив.

Для ES5 это удобно, потому что можно использовать:
- `for`;
- `while`;
- `Array.prototype.push`;
- `JSON.parse`;
- `Object.keys`.

------------------------------------------------------------
8. Пространства имён
------------------------------------------------------------

На MediaWiki-вики страницы делятся на пространства имён.

Примеры:
- основной namespace;
- User;
- File;
- Template;
- Category;
- Help;
- Talk.

Зачем это нужно:
- чтобы отличать статьи от шаблонов и служебных страниц;
- чтобы фильтровать только нужный тип страниц;
- чтобы не путать, например, статью и её обсуждение.

На практике в API часто нужно помнить:
- название может содержать префикс namespace;
- одна и та же строка может быть страницей в основном пространстве или служебной страницей;
- при автоматизации лучше работать не только с заголовком, но и с namespace id.

Пример логики:
- если обрабатываешь только статьи, исключай шаблоны и обсуждения;
- если работаешь с файлами, ищи только namespace File;
- если строишь индекс, сохраняй namespace отдельно.

------------------------------------------------------------
9. Изменение страницы: токены и редактирование
------------------------------------------------------------

Чтобы изменить страницу через API, обычно нужен токен.
Это защита от случайных или вредоносных изменений.

Общий порядок такой:
1) Получить токен.
2) Отправить POST-запрос на редактирование.
3) Проверить ответ.
4) Обработать ошибки.

Документация MediaWiki указывает, что токены нужны для изменяющих действий,
таких как редактирование, перемещение и подобные операции.

Пример общей идеи:

    action=query&meta=tokens

После этого можно отправить правку.

Редактирование обычно идёт через `action=edit`.
Что может быть в запросе:
- `title` — название страницы;
- `text` — новый текст или добавка;
- `token` — токен;
- `summary` — комментарий к правке;
- `format=json`.

Очень важно:
- изменение страницы почти всегда делается POST-запросом;
- GET для редактирования использовать не стоит;
- токен надо получать в той же сессии, где выполняется редактирование.

------------------------------------------------------------
10. Боты и бот-пароли
------------------------------------------------------------

Если скрипт будет много редактировать страницы, нужен особый подход.

На Fandom справка по ботам прямо указывает:
- бот — это внешний инструмент, который работает с вики не через обычный веб-интерфейс;
- API используется для получения данных и выполнения изменений;
- для автоматизации обычно используют отдельный бот-аккаунт или bot login;
- обычные учётные данные пользователя не предназначены для внешних инструментов;
- для входа через сторонние инструменты используют специальные bot credentials / bot passwords.

Практическое значение:
- не храни обычный пароль в скрипте;
- используй отдельные учетные данные для бота;
- держи минимально необходимые права;
- используй понятные edit summaries.

Это не только безопаснее, но и удобнее для отката и аудита.

------------------------------------------------------------
11. Что важно при работе с Fandom
------------------------------------------------------------

Fandom — это не отдельный язык и не отдельный API-стандарт, а площадка, где многие
вики работают на MediaWiki-основе.

Практически это означает:
- базовые Action API-запросы часто похожи на обычную MediaWiki;
- многие вики используют стандартные MediaWiki-модули;
- конкретные возможности могут отличаться от вики к вики;
- часть расширений и настроек зависит от конкретного сообщества и его конфигурации.

На практике это значит:
- сначала проверь, поддерживает ли вики нужный модуль;
- не предполагай, что все расширения везде одинаковые;
- тестируй запросы на конкретном домене вики;
- смотри на локальные правила сообщества.

Если автоматизируешь работу на Fandom:
- уважай правила конкретной вики;
- проверь, разрешены ли боты;
- не создавай лишнюю нагрузку;
- делай паузы между запросами.

------------------------------------------------------------
12. Полезные вики-сущности
------------------------------------------------------------

Для скриптов и ботов полезно понимать, какие сущности бывают в MediaWiki:

- page — страница;
- revision — версия страницы;
- category — категория;
- template — шаблон;
- file — файл;
- user — пользователь;
- talk page — страница обсуждения;
- namespace — тип страницы;
- token — защита для изменения данных.

Зачем это нужно:
- чтобы правильно формировать запросы;
- чтобы хранить результаты в структуре;
- чтобы не путать заголовок страницы и её идентификатор;
- чтобы понимать ответ API.

------------------------------------------------------------
13. Удобный шаблон JS ES5 для запросов
------------------------------------------------------------

Для ES5 удобно делать собственную обёртку над XMLHttpRequest.

Ниже — базовая схема:

    function apiGet(url, onSuccess, onError) {
        var xhr = new XMLHttpRequest();
        xhr.open("GET", url, true);

        xhr.onreadystatechange = function () {
            if (xhr.readyState !== 4) return;

            if (xhr.status >= 200 && xhr.status < 300) {
                try {
                    onSuccess(JSON.parse(xhr.responseText));
                } catch (e) {
                    if (onError) onError(e);
                }
            } else {
                if (onError) onError(new Error("HTTP " + xhr.status));
            }
        };

        xhr.send(null);
    }

Эта схема полезна, потому что:
- работает в старом ES5-коде;
- не требует fetch;
- легко расширяется;
- позволяет централизовать обработку ошибок.

Для POST можно сделать похожую функцию:

    function apiPost(url, data, onSuccess, onError) {
        var xhr = new XMLHttpRequest();
        xhr.open("POST", url, true);
        xhr.setRequestHeader("Content-Type", "application/x-www-form-urlencoded; charset=UTF-8");

        xhr.onreadystatechange = function () {
            if (xhr.readyState !== 4) return;

            if (xhr.status >= 200 && xhr.status < 300) {
                try {
                    onSuccess(JSON.parse(xhr.responseText));
                } catch (e) {
                    if (onError) onError(e);
                }
            } else {
                if (onError) onError(new Error("HTTP " + xhr.status));
            }
        };

        xhr.send(data);
    }

------------------------------------------------------------
14. Пример: чтение страницы
------------------------------------------------------------

Идея:
- сформировать URL;
- прочитать JSON;
- вытащить текст статьи;
- обработать его.

Псевдологика:

    var url = "https://example.fandom.com/api.php?action=query&prop=revisions&titles=Main_Page&rvprop=content&format=json";

    apiGet(url, function (data) {
        // найти страницу в data.query.pages
        // достать revision content
        // обработать строку
    }, function (err) {
        console.log("Ошибка:", err.message);
    });

Что обычно делают дальше:
- ищут нужные шаблоны;
- заменяют текст;
- строят статистику;
- проверяют наличие блоков.

------------------------------------------------------------
15. Пример: поиск и фильтрация
------------------------------------------------------------

Когда данные уже получены, с ними часто работают как с обычными массивами и объектами.

Например:
- собрать массив страниц;
- отфильтровать по namespace;
- преобразовать названия;
- отсортировать.

ES5-инструменты:
- `for`;
- `forEach`;
- `map`;
- `filter`;
- `reduce`;
- `sort`.

Пример:

    function onlyArticles(items) {
        var result = [];
        for (var i = 0; i < items.length; i++) {
            if (items[i].ns === 0) {
                result.push(items[i]);
            }
        }
        return result;
    }

Если структура ответа сложная, сначала удобно сделать:
- нормализацию;
- сбор в отдельный массив;
- потом уже обработку.

------------------------------------------------------------
16. Пример: правка страницы
------------------------------------------------------------

Редактирование требует:
- токен;
- POST;
- аккуратный текст;
- комментарий к правке.

Псевдошаблон:

    function editPage(apiUrl, title, text, token, summary, onSuccess, onError) {
        var body = [
            "action=edit",
            "title=" + encodeURIComponent(title),
            "text=" + encodeURIComponent(text),
            "summary=" + encodeURIComponent(summary),
            "token=" + encodeURIComponent(token),
            "format=json"
        ].join("&");

        apiPost(apiUrl, body, onSuccess, onError);
    }

Что важно учитывать:
- кодировать значения через `encodeURIComponent`;
- не забывать `summary`;
- проверять ответ на success / error;
- не делать лишних правок подряд.

------------------------------------------------------------
17. Работа с шаблонами
------------------------------------------------------------

Шаблоны — одна из ключевых частей wiki-экосистемы.

Они используются для:
- карточек;
- инфобоксов;
- навигации;
- служебных блоков;
- автоматической подстановки данных.

При работе с шаблонами важно понимать:
- имя шаблона может быть в пространстве Template;
- параметры шаблона могут быть именованными или позиционными;
- содержимое шаблона обычно хранится в wikitext;
- иногда удобнее читать уже разобранный HTML, а иногда именно wikitext.

Практический подход:
- если нужен сырой текст, бери revisions;
- если нужен рендер, бери parse;
- если нужен список страниц, связанных с шаблоном, смотри категорию или ссылочную структуру.

------------------------------------------------------------
18. Ошибки, которые часто возникают
------------------------------------------------------------

1) Сразу ожидать HTML там, где приходит wikitext.
   Нужно понимать, какой API-модуль ты используешь.

2) Не обрабатывать отсутствие страницы.
   В ответе может не быть нужной статьи.

3) Не кодировать параметры.
   Особенно в URL и POST-данных.

4) Не учитывать namespace.
   Из-за этого можно случайно читать не ту страницу.

5) Думать, что все вики одинаковые.
   На Fandom конкретная вики может иметь свои расширения и правила.

6) Делать много запросов подряд.
   Это плохо и может создать нагрузку.

7) Хранить обычный пароль в скрипте.
   Лучше использовать bot login / bot password.

8) Забывать про summary.
   Для правок это очень важно.

------------------------------------------------------------
19. Безопасный и аккуратный стиль автоматизации
------------------------------------------------------------

Хорошие правила:
- делать запросы по одному;
- проверять ответы;
- логировать ошибки;
- не спамить сервер;
- использовать понятные названия переменных;
- хранить конфигурацию отдельно от кода;
- не смешивать парсинг, сетевую логику и бизнес-логику в одну кашу.

Хорошая структура ES5-кода:
- `apiGet`
- `apiPost`
- `parsePageContent`
- `findPages`
- `editPage`
- `main`

Это делает код намного чище и понятнее.

------------------------------------------------------------
22. Уточнения и практический стандарт (обновление)
------------------------------------------------------------

22.1 MediaWiki vs Fandom: как правильно мыслить
- У большинства Fandom-вики базовый Action API остаётся MediaWiki-совместимым (`api.php`).
- Практическая разница чаще не в форме URL, а в правах, включённых расширениях, локальных правилах,
  лимитах и конфигурации конкретной вики.
- Надёжный подход: считать ядро API общим, а локальные детали — переменными.

Правило для кода:
- не предполагай, что «поле/модуль всегда есть»;
- сначала проверяй наличие данных в ответе;
- при отсутствии поля делай мягкий fallback, а не аварийное падение.

22.2 Что считать важными отличиями Fandom на практике
- bot credentials (bot passwords) нужно рассматривать как основной путь для внешних инструментов;
- права и ограничения могут отличаться от вики к вики;
- даже при одинаковом модуле API рабочая логика сообщества и шаблонов может быть разной.

Итог:
- проверяй права пользователя/бота перед массовыми операциями;
- не переноси поведение одной вики на другую без теста;
- обрабатывай предупреждения API и лимиты как ожидаемую часть сценария.

22.3 Rate limit и безопасная скорость
Практический безопасный профиль для долгоживущих скриптов:
- чтение: держать до 3 одновременных запросов;
- запись: около 1 правки в секунду или медленнее;
- при `429` или `ratelimited`: backoff + уважение `Retry-After`;
- массовые операции: маленькие пачки + паузы;
- большие выборки: через `continue`, а не «всё сразу одним запросом».

22.4 Браузер vs внешний бот (CORS, cookies, same-origin)
В браузерном ES5-коде чаще всего ломается именно доступ между доменами.
- Cross-origin запросы требуют корректного CORS;
- для публичных чтений часто используют `origin=*`;
- авторизованные сценарии зависят от cookie/credential политики;
- same-origin/samesite ограничения особенно важны при межсайтовых сценариях.

Во внешнем боте (не браузер):
- CORS как браузерное ограничение обычно не мешает,
  но остаются токены, cookies-сессия, лимиты и авторизация.

22.5 Защита от edit conflict: обязательный минимум
Для надёжной записи:
1) прочитать текущую версию страницы;
2) получить `revid` и/или `timestamp`;
3) при `action=edit` передавать `baserevid` или `basetimestamp`;
4) передавать `starttimestamp`;
5) при конфликте перечитывать страницу и повторять цикл.

Конфликт правки — это нормальный рабочий сценарий, а не критическая авария.

22.6 Минимальный безопасный стандарт для бота
- dry-run режим (показать, что будет изменено, без записи);
- idempotent-правки (повторный запуск не дублирует изменения);
- audit log (что именно, когда и почему изменено);
- backoff и паузы;
- понятный `summary`;
- обработка частичных успехов;
- возможность остановить серию правок без порчи состояния.

22.7 Что считать устойчивым, а что хрупким в ответах API
Обычно устойчиво:
- каркас Action API (`api.php`);
- базовые операции `query`, `parse`, `edit`;
- continuation-механизм `continue`;
- базовая структура `query.pages`;
- стандартные поля ошибок/предупреждений.

Обычно хрупко:
- расширенные поля из локальных расширений;
- HTML из `parse` (может меняться по вики и по времени);
- шаблонные соглашения конкретного сообщества;
- локальные права, namespaces и правила.

22.8 Практика по шаблонам: когда revisions, когда parse
- `revisions` — когда нужен исходный wikitext;
- `parse` — когда нужен фактический рендер (HTML);
- `prop=templates` — когда нужен список задействованных шаблонов;
- комбинируй режимы, если проверяешь и источник, и итоговый вид.

22.9 Короткая формула для запоминания
«Ядро MediaWiki API в целом стабильно, локальная конфигурация плавает.
Читай через query/revisions, рендер через parse, редактируй через edit + токен + защита от конфликтов.
В браузере учитывай CORS/cookies, в боте — лимиты, continue, backoff, logging и dry-run».

На Fandom есть MediaWiki:ImportJS.

Это служебная страница, через которую можно подключать JS-файлы.
Обычно она используется как список страниц, которые нужно импортировать.

По справке Fandom, эта страница позволяет импортировать скрипты с локальной вики и с Fandom Developers Wiki, а строка должна содержать имя статьи без префикса MediaWiki:.

2.6 Lua-модули

Lua живёт в:

Module:Имя

А вызывается из шаблона так:

{{#invoke:ИмяМодуля|функция}}

Lua в MediaWiki реализуется через Scribunto, и MediaWiki официально описывает его как механизм для встраивания скриптового языка в страницы. Scribunto использует Lua 5.1.
Это не ES5, не JS и не CSS. Это отдельный слой логики для шаблонов.

4.1 Lua — не JS

Lua-модули нужны для:

форматирования данных;

4.2 Где живёт Lua

Module:Something

4.3 Как вызывается

{{#invoke:Something|main}}

4.4 Что важно помнить

Lua-модуль вызывается из wikitext;

ошибки Lua часто ломают шаблонный вывод;
его надо тестировать как часть вики-разметки.

JS в Common.js — клиентский код;
CSS в Common.css — стили;
Lua в Module: — серверная шаблонная логика;
wikitext — язык разметки страниц;
API — отдельный HTTP-интерфейс.
ОСОБЕННОСТИ FANDOM, КОТОРЫЕ ОТЛИЧАЮТ ЕГО ОТ “ПРОСТОГО JS”

5.1 Fandom — это не JS-проект

Если смотреть только на код, легко ошибиться.
На Fandom всё завязано на:

namespaces;
шаблоны;
категории;
редиректы;
права пользователей;
конкретные правила сообщества;
MediaWiki-интерфейс.

5.2 Контент — это не HTML и не JS

Основной исходник страницы — это wikitext.
HTML появляется потом, после парсинга.

Из этого следуют отличия:

нельзя просто “искать div’ы” в исходнике;
нельзя думать, что всё лежит в DOM, если ты работаешь с исходным текстом;
шаблон может генерировать большой HTML-блок;
один параметр шаблона может влиять на целую страницу.

5.3 Страницы — это объекты с namespace

Например:

Main: — основное пространство
User:
Template:
Category:
File:
Module:
MediaWiki:

Это не просто слова в названии.
Это разные типы страниц с разными смыслами и правами.

5.4 Вики меняется не только кодом

На Fandom поведение страницы может меняться через:

шаблоны;
Lua;
CSS;
JS;
настройки skin;
гаджеты;
локальные сообщения системы.

То есть “изменить страницу” можно не только редактированием HTML или JS.

5.5 Локальные правила важнее абстрактной логики

На разных Fandom-вики:

могут по-разному оформлять инфобоксы;
могут использовать разные шаблоны;
могут запретить определённые правки;
могут иметь свои стандарты именования;
могут требовать особый формат summary.

ЧТО НУЖНО ПОНИМАТЬ ПРО ШАБЛОНЫ И ИХ ПАРСИНГ
шаблоны могут вызывать Lua;
Lua может формировать сложный HTML;
CSS потом этот HTML оформляет;
JS может ещё и менять интерфейс после загрузки.

Из-за этого один и тот же блок может быть:

вики-разметкой;
шаблонным вызовом;
Lua-генерацией;
HTML-результатом;
CSS-оформлением;
JS-поведением.

Это нужно помнить, чтобы не путать источник проблемы.

ЧТО САМОЕ НЕОБЫЧНОЕ В FANDOM ПО СРАВНЕНИЮ С ПРОСТЫМ JS

14.1 Код — это страница

На Fandom твой “файл” может быть страницей MediaWiki:Something.js.

14.2 Интерфейс — это часть вики

Если меняешь CSS/JS в wiki namespace, меняешь поведение сайта для пользователей.

14.3 Контент и код тесно перемешаны

Шаблоны, Lua, CSS, JS и wikitext работают вместе.

14.4 Есть отдельные правила публикации и правки

Не всё редактируется кем угодно.

14.5 Есть пользовательские и общие уровни

То, что работает для одного пользователя, может не работать для всех.

14.6 Модульность часто идёт не из файловой системы, а из страниц

ImportJS, Common.js, User pages, Module namespace — это не обычный проектный layout.

Fandom — это не “просто сайт с JS”.
Это среда, где одновременно живут:

вики-контент,
шаблоны,
Lua,
общие скрипты,

Если Codex это понимает, он будет гораздо полезнее:

не будет путать JS с wikitext;
не будет путать Common.js с User:.../common.js;
не будет путать CSS-страницы с обычными файлами;
не будет ломать шаблоны, когда нужно менять только интерфейс;
не будет пытаться решать вики-задачи как обычные фронтенд-задачи.
